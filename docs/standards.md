# Coding Standards

See the platform-wide [`coding_style_rules.md`](coding_style_rules.md) for the full reference. This page summarises the rules most relevant to this service.

## Formatting

- **Line length**: 100 characters max
- **Import groups**: three blocks — stdlib, third-party, internal (separated by blank lines)
- **Gofmt/goimports**: enforced by `golangci-lint` on every commit

## Naming

- `camelCase` for unexported symbols
- `PascalCase` for exported symbols
- Initialisms fully capitalised: `userID`, `tenantID`, `workflowXML`, `GetWorkflowByID`

## Logging

All service and handler code uses the `port.Logger` interface with `map[string]any` fields:

```go
// Correct
log.Error("publish failed", map[string]any{
    "error":     err.Error(),
    "tenant_id": tenantID.String(),
})

// Wrong — never format into the message string
log.Error(fmt.Sprintf("publish failed for tenant %s: %v", tenantID, err), nil)
```

`app.go` constructs the logger via `logger.NewLogger(cfg.AppEnv)` and passes the same `port.Logger` value into `gincommon.Config{Logger: log}` and all service/handler constructors.

## Error handling

- Wrap errors at boundary crossings: `fmt.Errorf("publish workflow: %w", err)`
- Define sentinel errors in `core/domain/errors.go`; check with `errors.Is`
- HTTP handlers map domain errors to RFC-9457 ProblemDetails responses

## Testing

- **Table-driven tests** for all unit tests
- **Integration tests** live in `test/integration/` and use testcontainers (no build tags required — they are run by `make test-integration`, not `make test`)
- **Mocks** generated by GoMock (`make mock`) — never hand-written for the service layer; handler and adapter layers use hand-rolled fakes (see CLAUDE.md #11 and #17)
- Coverage threshold: **95%** enforced by `make cover` in CI (excluding postgres adapter and generated packages)

## Architecture rules

- `core/` packages have zero dependencies on `adapter/` or external frameworks
- All external I/O (DB, cache, HTTP, gRPC) crosses through a `port` interface
- Service and handler constructors accept interfaces, not concrete types
- Repository adapter constructors (`NewWorkflowRepo`, etc.) accept `*pgcommon.Pool` — the sqlc/pgcommon pattern is an intentional exception to the interface rule at the DB adapter layer
- `app.go` is the only file that wires concrete adapters to interfaces

## BPMN compilation

- A userTask's department is derived from its **lane membership** — the lane it appears in via `<bpmn:flowNodeRef>`. No `dept_id` Zeebe property is used. Lane `name` → `DepartmentDef.ID` and `DepartmentDef.Label`. The Profile Service owns the format; the compiler trusts it as-is.
- Stage type comes from **`zeebe:taskDefinition type`** (e.g. `type="prep"`), not from a custom property. The allowed values are configured via the `StageTypeHandler` registry — not hardcoded — so the Membership Service can evolve the set without a compiler change.
- Role and default assignees come from **`zeebe:assignmentDefinition`** (`candidateGroups` → role, `candidateUsers` → default assignees), using the standard Camunda 8 assignment element instead of custom Zeebe properties.
- **XOR gateways + `<bpmn:conditionExpression>`** are for routing decisions (explicit path choices: bid vs no-bid, value thresholds, etc.). **Error boundary events on subprocesses** are for stage rejection / rework flows — the approve-stage worker signals rejection via an error code, caught by the boundary event.
- Collaboration (multi-pool) BPMN is supported: each `isExecutable="true"` participant compiles to a separate `CompiledPlan` wrapped in a `CompiledCollaboration`. Message flows compile to `MessageDef` entries linking plans by message name.
- The parser enforces namespace declarations (`MISSING_NAMESPACE`) and the Tier-3 element denylist (`REJECTED_ELEMENT`) on the raw XML token stream — unknown elements are dropped by `encoding/xml`, so the denylist scan must happen before unmarshal.
- See [BPMN Workflow Specification](bpmn-spec.md) for the full element reference and [BPMN Validation & Compilation](bpmn-validation.md) for the validation rule catalog and error-code set.
